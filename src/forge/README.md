# forge

The runner that carries a goal across however many bounded sessions it takes, without ever letting a failure buy a bigger model.

## What a run guarantees

Each session has a token ceiling for its class, read from `model-policy.json` (triage, plan, implement, verify, and the rest each get their own `maxContext` and `maxTurns`). When a session crosses its ceiling, it does not retry or move up to a heavier tier. `worker.ts`'s docstring calls a goal "a chain of bounded sessions": at the ceiling "the worker asks the session to write a handoff packet and starts a successor seeded with it, on the same model." Model-tier selection reads no failure history, which is what makes "no escalation by retry" a property of the mechanism rather than a promise someone has to keep: `model-policy.json` states it directly with `"escalation": "never-by-retry"`. That is a separate counter from `sessionsSinceCommit`, which `worker.ts` does track and which parks a chain once three sessions in a row land no commit.

The successor's environment is the parent's, minus a fixed set. `worker.ts` copies the whole parent environment, then deletes nine inherited markers (the session id, the child-session flag, the PID, the effort level, the messaging socket and token, and the CLI identity markers) so a child cannot be mistaken for the session that spawned it. `ANTHROPIC_API_KEY` is deleted too, and separately: "not because it is one of the nine: with a key present the child bills the API account instead of using the subscription login." The config directory gets its own treatment. `launcher.ts` states the same rule ("sharing the interactive session's directory means the fleet writes into the store" the person at the keyboard is using), but its `launchEnv` only feeds a `forge run --dry-run` diagnostic line. The pin that actually reaches a live worker is set independently in `sdkengine.ts`'s `buildWorkerOptions`, which sets `CLAUDE_CONFIG_DIR` to the fleet directory instead of passing through whatever the parent had.

## What the launcher refuses before a run starts

`checkLaunch` refuses an empty condition: "the condition is empty, so the goal has no way to end." In practice `forge run` never hits that branch, since it substitutes a default condition text before calling `checkLaunch`; the check only fires when something calls `checkLaunch` directly. A condition over the 4000 character limit is refused for real, so it can't get silently truncated instead of failing loudly. A launch is also refused while a `claude login` is in flight on the account, since "starting now races the credential this worker is about to use," and while the kill switch is engaged. A brief that opens a websocket Monitor is refused outright too: "a queued event kills a `-p` process mid tool call and a worker has no console to watch." `forge run` also refuses before any of this, at argument parsing, when `maxContext` or `maxTurns` doesn't parse: a NaN ceiling never fires.

## The kill switch

`forge stop --all` is the one command documented as having to work "when nothing else does." It does not kill outright: `Fleet.stopAll` engages the kill switch file, then sorts the registry's rows into three outcomes. A row this process holds a live session for directly gets the handoff request sent and raced against an idle budget, and the session is stopped either way; a row with no live session (the ordinary case, since `forge stop` is its own process) gets the same request queued into that run's inbox instead, "where the run's own PreToolUse hook delivers it on the next tool call and the run parks itself." A registry row whose pid is no longer alive is neither of those -- it is reported as stale, not as reached or unreachable, because nothing is there to stop. `reached` and `unreachable` both describe a row that was live at the moment `stopAll` looked; stale is the third case, a row `processAlive` already says is gone.

The switch itself is honoured in two more places, not only by `stopAll`'s own send. The PreToolUse hook in `sdkengine.ts` checks it ahead of every tool call and, on a hit, denies the call and answers with the handoff request as `additionalContext`, journaling `permission.denied` with the reason `"the fleet kill switch is engaged"`. `worker.ts`'s own turn loop polls the same switch on every turn of a segment, "checked after done and the ceiling, so a turn that already finished or already needs a handoff for its own reason is not relabelled a kill," and a run parked and waiting for a person to answer an ask polls it too, on the same interval as the inbox poll, so "the kill switch... and a `SIGINT`" are the only two things that end that wait early. The CLI's own help text states the goal, not a guarantee already met for every lane: it will "park every run with a handoff and end all spend."

## How a worker is spoken to

Two channels exist for two situations. An ordinary message to a running worker gets queued in a per-run inbox and rides along as `additionalContext` on that worker's next tool call. It is never delivered by interrupting the worker, and never denied: "a message is information, and turning it into a refusal would make telling a worker something an act of stopping it." A message sent while the worker is idle between tool calls just waits for the next one.

A question works differently. A worker cannot block on a prompt, so when one is raised, it is intercepted before it renders, written to a keyed inbox entry, and the run parks with its work committed and its lane released. The keying follows the ask's `kind`, not which code raised it: an ordinary `question` ask is keyed on its goal, run, and action target together, so it gets its own entry even when another run asks the same words. `forge_ask` defaults to `question` but its schema lets a worker set `kind: 'blocker'` too. A `blocker` ask, which is what `drift.ts` always raises when a branch can no longer merge cleanly against its base or its mergeable state cannot be read at all, is keyed on wording alone, so every run stuck behind the same wall shares one entry instead of one each. Answering an entry queues the resume text into the goal's own inbox (falling back to the run's, when an ask recorded no goal) and, when the same process still holds the live session, resumes it in place.

## What this module does not cover

`liveness.ts` describes itself, unactuated, as a pure sensor: "parks, kills and nudges nothing, that stays the Warden's job. This only watches and says so." That line covers the module only when no `WardenActuator` is wired in. Give it one, and `actOnStuck` does park a stuck run and flag its lane on an idle, tool-budget, or context trip, on the Warden's behalf rather than the module's own. Drift and blocker handling exist too, in `drift.ts`, and a console exists, served by `server.ts`. `contracts.ts` names governor, intake, and council as event-bus roles; council now has the implementation the sections below describe, and `governor.ts` and `src/forge/intake/` both carry real code of their own, but neither yet has the production call site its role implies -- `buildBurnLedger` and `checkConformance` are called from `cli.ts` and the Warden tick, and `runIntakeOnce` runs against whatever feeds `forge intake --once` is handed, which today is none: "no real per-source client exists yet."

## The Warden tick

`forge up`'s liveness cadence used to only watch. `WardenTick.run` is what turned watching into acting (P4.7/I2): each call reports fleet health, then walks the open trips `liveness.ts` flagged, calls `actuator.park` on the ones registered to a real run, and checks conformance and any credential that has come back valid, "each step guarded so one throw never stops the rest." A trip's key gets a cheap pre-check against the registry before the tick ever calls the actuator, but that check is an optimisation, not the decision of record: I11b's own incident (the pre-check and the actuator's own registration check read the same registry a beat apart and disagreed) is why "the journal is decided from the actuator's real answer, never from the pre-check that got it to call the actuator." Only `WardenActuator.park` is ever reached from here; a kill still needs a `decision.made` row a person wrote with `forge decide`, "which this tick never manufactures."

## The Reasoner

Every seam that needs a model's answer -- the Warden tick's conformance drift, the console router, `forge council` and `forge gate`, `forge reason` itself -- calls the same `Reasoner` contract rather than its own copy of the SDK. `ClaudeReasoner.call` is "one bounded, single-turn session through the same SDK `query` the runner uses," which is `Engine`'s injectable `QueryFn` in `src/adapter/engine.ts`, never a mock of the reasoner class itself. It asks for a JSON reply shaped `{"text": ...}` but does not insist on it: a lens reply declared `replyShape: 'array'` is accepted as-is, and a well-formed JSON object missing the `text` key still gets its whole body re-stringified into one, "a worse failure than one that accepts it and derives `text` from the whole object." The `codex` provider is deliberately unimplemented: `CodexReasoner.call` returns a clear "not configured" error without spawning a subprocess, because the one sanctioned route to Codex is `dev-harness/tools/codex_call.py`, and this is not it.

## The council and gate verbs

`forge council --repo OWNER/NAME --pr N` reviews a PR that is already green: it refuses outright when `repoAllowedForCouncil` says the repo is not on the review allow-list, and again when the PR's own checks are not `conclusion: 'success'` on the head it just read. Past that it builds one rule verdict from `evaluateAction`, runs the lens-and-judge round through the same `Reasoner`, and writes an attestation keyed to that head and base. `forge gate --repo OWNER/NAME --pr N` is the merge-time reader of that attestation, not a second review: it refuses when no attestation exists for the PR's current head, when the attestation is for a head or base the PR has since moved past, when its verdict is `FIX FIRST`, or when the checks it reads now disagree with what the attestation saw. Only past every one of those does `--merge` do anything.
